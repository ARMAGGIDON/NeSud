# Перевірка, приймання та залишкові обмеження

## Локальний цикл

```powershell
npm --prefix src/NeSud.Server install --ignore-scripts --no-audit --no-fund
npm --prefix src/NeSud.Server run prepare-web
npm --prefix src/NeSud.Server run test:realtime
dotnet build NeSud.slnx
dotnet run --project tests/NeSud.SmokeTests -c Release -- 3
```

Запустити сервер на http://localhost:5080 (для API smoke окрема тестова БД, щоб не засмічувати реальний рейтинг), у другому терміналі:

```powershell
npm --prefix src/NeSud.Server run test:realtime:live
pwsh -File tests/api-smoke.ps1
```

Smoke-сценарії: Generation, Game, Storage, Rules, Rewards, Challenges, Social, Identity, SmtpEnv. Перевіряють логічну складність, єдиність, міграцію, ідемпотентність, ресурси, життєвий цикл, спільну дату, статистику, реферальні винагороди, аватар та конфігурацію SMTP. Realtime unit: snapshot/pulse, delta, неправильна ревізія. Live: двійковий WebSocket, авторизація, ізоляція, push між клієнтами та REST, конфлікт, logout.

## Докази попереднього стану

У локальному логу користувача від 27.11.2026: збірка всіх п'яти проєктів успішна, 12 згенерованих головоломок (по три на рівень), усі виведені smoke-сценарії PASS, SQLite 3.54.0, три JS unit PASS, live SignalR PASS і API smoke PASS. Це підтвердження стану до SMTP та подальшої переробки профілю/шапки, а не автоматична гарантія поточної версії. Пізніші скриншоти показують робочий профіль, підтверджену пошту та аватар. Нова збірка та smoke після останніх правок потребують локального виконання.

## Відкладені задачі / не підтверджено

- Візуальне і системне приймання поточного HEAD у Windows/браузері.
- Реальні вимірювання CPU, RAM, P95/P99, SQLite I/O і трафіку; SignalR не є доказом прискорення без бенчмарку.
- Desktop SignalR, безпечне продовження чернеток іншого клієнта, масштабування за межі одного процесу.
- Доставка SMTP залежить від реальної конфігурації провайдера. Немає автоматичного надсилання тестових листів у smoke.
- Аватари інших гравців можуть залишатися застарілими в кеші; перевірка шапки/профілю Desktop періодична.
- Довгий результат генерації Hard/Expert можливий; генерація не підмінює рівень простішою головоломкою.
- Демонстраційна реклама, евристичний аудит швидкості та неперевірені офлайн-результати мають свідомі межі.

Додано регресії приватної проєкції активних ігор: окремі Web, Desktop та щоденні сеанси, ізоляція акаунтів, відсутність розв'язку, виключення завершеної гри, HTTP 401 без токена. Потребують локального виконання. Ручна перевірка: стабільність шапки, Mouse 4/5 у звичайній/щоденній грі та навігації, відсутність приватних блоків у чужому профілі, локальна історія без сервера, продовження активних ігор.


## Завершення сервера

Після збірки сервера на Windows запустіть його у першому терміналі, а у другому виконайте `npm --prefix src/NeSud.Server run test:shutdown -- --manual`. Після READY натисніть Ctrl+C один раз у першому терміналі. Очікується закриття обох активних WebSocket, недоступність HTTP і повернення prompt сервера. Тест не створює акаунтів чи ігор. На Linux `npm --prefix src/NeSud.Server run test:shutdown` запускає Debug DLL з тимчасовою SQLite БД, надсилає SIGINT процесу та додатково перевіряє нормальний exit code. Сценарій потребує фактичного локального виконання; синтаксична перевірка не підтверджує завершення процесу.


### Діагностика Ctrl+C у Windows

Якщо prompt повертається без повідомлення про завершення або Ctrl+C спрацьовує нестабільно, увімкніть `NESUD_SHUTDOWN_TRACE` (абсолютний шлях до тимчасового файлу). Сервер записує PID, часові мітки та незалежні від ILogger події Process.start, Run.enter, ApplicationStarted, ApplicationStopping, ApplicationStopped, Run.return, ProcessExit. Діагностика не змінює обробку сигналів, shutdown timeout або WebSocket. Порівняйте запуск через dotnet run та прямий запуск DLL з однакового робочого каталогу, спочатку в IDE, потім у звичайному Windows Terminal. Натискайте Ctrl+C один раз, перевіряйте prompt, код завершення та trace. Відсутність ApplicationStopping не підтверджує конкретну причину, а лише відсутність зафіксованого штатного початку зупинки; наявність ApplicationStopped та Run.return підтверджує завершення host. Не використовуйте тестову трасу на мережевому диску. Логи не містять токенів чи адрес БД.
